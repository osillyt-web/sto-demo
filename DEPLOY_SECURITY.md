# Как закрыть файлы и папки сайта от посторонних

Коротко: **прятать — нельзя, закрывать доступ — можно.** Любой адрес, который браузер может открыть,
может открыть и человек, и сканер. Задача не «сделать незаметным», а «сделать недоступным на сервере».

---

## 1. Что в этом проекте уже сделано

| Механизм | Как работает |
|---|---|
| **Маршруты по списку** | Сервер отвечает только на известные адреса (`/`, `/cases`, `/services/...`, `/brands/...`, `/privacy`, `/admin`, `/api/...`). Всё остальное — 404. Никакой привязки «путь → файл на диске» нет. |
| **Статика только из `static/`** | Путь канонизируется, проверяется, что он физически внутри `static/`, запрещены `..`, `:`, обратные слэши, точки в начале, выход за пределы каталога. Разрешены только расширения `.css .js .webp .png .jpg .jpeg .gif .svg .ico .woff .woff2 .ttf .map`. |
| **Список запрещённых имён** | Любой запрос, похожий на попытку достать исходники, базу, настройки или репозиторий (`data`, `backups`, `templates`, `tools`, `.git`, `.env`, `*.py`, `*.db`, `*.sqlite`, `*.log`, `*.bak`, `*.pem`, `*.key`, `auth.json`, …), получает **тот же 404**, что и несуществующая страница. |
| **Никаких подсказок** | Ответ на служебный путь неотличим от обычной несуществующей страницы: ни 403 «есть, но нельзя», ни списка каталога, ни текста ошибки с путём к файлу. |
| **Журнал попыток** | Каждая такая попытка пишется в `data/security.log`: время, IP, метод, путь, причина. Счётчик доступен владельцу в `/api/health` (только с входом). |
| **Без версии Python** | Заголовок `Server` больше не содержит версию Python: точная версия облегчает подбор известных уязвимостей. |
| **Лишнее не отдаётся** | `/api/health` без входа не показывает количество заявок и настроек; при ошибке базы наружу уходит короткий статус, а текст ошибки (с путями) — только в журнал и владельцу. |

Проверка на живом сервере: 25 служебных адресов (включая `..`, `%2e%2e`, `::$DATA`, `.git/config`, `.env`,
`/data/sto.db`, `/templates/index.html`) — все отдают 404, а все 31 файл из `static/` открываются как раньше.
Это закреплено автотестами проекта.

## 2. Главное правило для настоящего хостинга: разделить «публичное» и «служебное»

Пока сайт обслуживает сам Python-сервер, он физически не умеет отдать произвольный файл.
Но как только перед ним встанет nginx или Apache (а на VPS так и будет), защищать нужно уже их.

Правильная раскладка — **в корне сайта только то, что можно показывать**:

```
/srv/autotochka/
├── public/            ← КОРЕНЬ САЙТА (document root)
│   ├── static/        (css, js, картинки)
│   ├── robots.txt
│   └── sitemap.xml
└── app/               ← ВЫШЕ корня, снаружи веба
    ├── server.py, content.py, ops.py
    ├── templates/
    ├── data/          sto.db, auth.json, security.log
    ├── backups/
    └── .env
```

Даже если в правиле веб-сервера ошибка, файлы из `app/` недостижимы: их просто нет в дереве, которое отдаётся.

### nginx

```nginx
server {
    server_name example.com;
    root /srv/autotochka/public;          # только публичное

    # служебные и «мусорные» файлы — всегда 404
    location ~ /\.            { return 404; }   # .git, .env, .htpasswd
    location ~* \.(py|db|sqlite|log|bak|ini|env|pem|key|jks|keystore)$ { return 404; }
    location ~* ^/(data|backups|templates|tools|scripts)/ { return 404; }

    # без списков каталогов
    autoindex off;

    # не показывать версию nginx
    server_tokens off;

    location /static/ {
        expires 7d;
        add_header Cache-Control "public";
        try_files $uri =404;
    }

    location / { proxy_pass http://127.0.0.1:8000; proxy_set_header Host $host;
                 proxy_set_header X-Real-IP $remote_addr; }
}
```

### Apache (`.htaccess` в корне сайта)

```apache
Options -Indexes
ServerSignature Off

<FilesMatch "\.(py|db|sqlite|log|bak|ini|env|pem|key|jks|keystore)$">
  Require all denied
</FilesMatch>
RedirectMatch 404 /\.(git|env|htpasswd)
RedirectMatch 404 ^/(data|backups|templates|tools|scripts)/
```

### Render / PaaS

Там нет отдельного веб-сервера: приложение само отвечает на запросы. Значит работает то же,
что уже встроено в `server.py`, плюс: переменные окружения (`.env` не заливать), база — на постоянном
диске, а не в папке со статикой, и `SITE_URL` выставлен в настоящий домен (иначе `sitemap.xml` и
`canonical` будут указывать на `127.0.0.1`).

## 3. Способы, которые работают, и их цена

| Способ | Что даёт | Ограничение |
|---|---|---|
| Список разрешённых маршрутов (уже есть) | посторонние пути физически не обслуживаются | нужно поддерживать при добавлении страниц |
| Разделение корня сайта и приложения | самая надёжная защита от «случайно открыл папку» | требует правки при переносе на VPS |
| Запрет по шаблонам в nginx/Apache | закрывает `.git`, `.env`, базы, бэкапы | одна ошибка в регулярке — и защиты нет; нужен тест после настройки |
| Отключение списков каталогов | не покажет дерево файлов | не закроет конкретный файл, имя которого угадали |
| 404 вместо 403 | не подтверждает существование файла | косметика, но полезна против перебора |
| Ограничение частоты запросов | перебор становится невыгодным (`limit_req`, fail2ban, Cloudflare Rate Limiting) | настраивается на уровне сервера |
| Basic-auth или IP-allowlist на `/admin` и на тестовый стенд | панель не видна даже при утечке адреса | неудобно при работе с телефона |
| WAF (Cloudflare и подобные) | режет типовые сканеры по сигнатурам | платно/зависимость от посредника |
| Журнал + оповещение о всплеске 404 | вы узнаёте о переборе, а не постфактум | нужно смотреть, а не только писать |
| HTTPS + HSTS | трафик нельзя прочитать по дороге | сертификат и настройка |
| Бэкапы вне корня сайта и вне репозитория | утечка копии не отдаёт базу | нужно проверять, что копии действительно не в вебе |

### Что НЕ работает как защита

- **`robots.txt` с `Disallow`.** Он не запрещает доступ, а **публикует список** того, что вы прячете.
  Первое, что читает сканер, — именно `robots.txt`. Для случайных страниц используйте `<meta name="robots" content="noindex">`,
  но помните: `noindex` мешает попасть в поиск, а не открыть адрес.
- **Секретный адрес панели.** Полезен как дополнительный слой, но перестаёт помогать, как только адрес
  попал в чужой лог, скриншот, историю браузера или в переписку.
- **Скрытые ссылки и `display:none`.** Всё, что находится в HTML, видно в исходнике страницы.
- **Хеширование имён файлов «чтобы не угадали».** От перебора по словарю не спасает.

## 4. Чек-лист перед сдачей клиенту

- [ ] Корень сайта содержит только публичные файлы; код, база, бэкапы и `.env` — выше него.
- [ ] В репозиторий не попали `data/`, `backups/`, `.env`, ключи, `*.db` (есть `.gitignore`).
- [ ] `.git` не опубликован (`https://домен/.git/config` → 404).
- [ ] `/data`, `/backups`, `/templates`, `/tools`, `*.py`, `*.db`, `*.log` → 404.
- [ ] Нет списков каталогов (`/static/` не показывает файлы).
- [ ] Заголовок `Server` без версий nginx/Python.
- [ ] Админка закрыта паролем, есть ограничение попыток входа, включён HTTPS.
- [ ] Ошибки не показывают пути и трассировки, а пишутся в журнал.
- [ ] Настроено оповещение о всплеске 404 и о неудачных входах.
- [ ] Бэкапы лежат вне корня сайта, восстановление проверено.

## 5. Как проверить, что закрыто

```bash
# быстрый набор «плохих» адресов: все должны дать 404
for p in /data/auth.json /data/sto.db /.git/config /.env /server.py /backups/ \
         /templates/index.html /tools/axe_check.py /static/../data/auth.json \
         "/static/style.css::\$DATA"; do
  printf "%-38s %s\n" "$p" "$(curl -s -o /dev/null -w '%{http_code}' "https://домен$p")"
done
```

В проекте это уже автоматизировано: `python test_flow.py` (раздел «защита служебных файлов»)
и журнал `data/security.log`, куда попадают все попытки.
