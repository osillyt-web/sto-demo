## Как это устроено

Тип сайта в панели всегдадаты остался **PHP** (переключить на Python WSGI не удалось: рабочий
стол Windows был заблокирован, GUI-автоматизация недоступна), поэтому работает схема «PHP → Python»:

1. `~/www/index.php` — прокси: принимает HTTP-запрос, передаёт его локальному процессу
   Python (`127.0.0.1:8500`) через curl, возвращает ответ без изменений.
2. Если процесс не отвечает, `index.php` сам его запускает (`shell_exec`) и ждёт до 6 с.
   Проверено: после принудительной остановки сайт восстановился за 0,46 с.
3. `.htaccess` — `FallbackResource /index.php` (все пути, кроме реальных файлов, идут в прокси),
   плюс запрет отдачи `*.py`, `*.db`, `*.log`, `*.pid`, каталогов `data/`, `backups/`.
4. `~/www/.env` — `PORT=8500`, `HOST=127.0.0.1`, `SITE_URL=https://osillytweb.alwaysdata.net`
   (без него sitemap и канонические ссылки отдавали `127.0.0.1`).

### Важно про окружения alwaysdata

Процесс из PHP-прокси живёт в **web-окружении**, а SSH-сессия его не видит (`ps` пуст).
Это нормально: процессом управляет прокси, а не SSH.

### Урок про перезапуск на alwaysdata

`restart.sh` по SSH **не заменяет** процесс, который обслуживает сайт: он живёт в web-окружении
и в `ps` SSH-сессии не виден. Симптом: файлы обновлены, а сайт отдаёт старый код
(в HTML оставались незаменённые `{{REVIEWS_HEAD}}`, `/reviews` → 404).
Правильный порядок: положить в `~/www` временный PHP-скрипт, который делает
`pkill -f server.py` и заново запускает приложение, вызвать его по HTTPS, затем удалить.
После этого первый же запрос поднимает процесс с новым кодом (проверено: `uptime_s=1`, `/reviews` → 200).
